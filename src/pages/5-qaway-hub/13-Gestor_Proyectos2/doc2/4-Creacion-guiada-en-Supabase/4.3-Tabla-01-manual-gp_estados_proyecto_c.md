# 4.3 · TABLA 01 (manual) — `gp_estados_proyecto_c`

**Ejercicio 1 de 2.** Se crea **a mano desde el panel**, sin SQL, para tocar con los dedos lo que
luego el SQL hará de golpe.

- **Qué es:** catálogo global de los estados que puede tener un proyecto.
- **Dependencias:** ninguna. No tiene claves foráneas.
- **Justificación:** §2 fila 1 de `4.2-Criterios-y-justificacion-de-catalogos.md`.
- **Aviso de paridad:** la tabla debe quedar **idéntica** a la definición del archivo
  `20261112_0001_gp_catalogos_base.sql`. Si aquí se agrega algo (por ejemplo un `CHECK` sobre
  `codigo`), se agrega también allí. No se crea nada "solo en el panel".

---

## Paso 1 · Crear la tabla en Table Editor

1. Supabase → **Table Editor** → botón **New table**.
2. **Name:** `gp_estados_proyecto_c`
3. **Schema:** `public`
4. Activar **Enable Row Level Security (RLS)** ahora (si el panel lo permite al crear; si no,
   se activa en el paso 4).
5. En la grilla de columnas, cargar exactamente estas 9 filas:

| # | Name | Type | Default value | Nullable | Primary key |
|---|---|---|---|---|---|
| 1 | `id` | `uuid` | `gen_random_uuid()` | ❌ no | ✅ sí |
| 2 | `codigo` | `text` | *(vacío)* | ❌ no | ❌ no |
| 3 | `nombre` | `text` | *(vacío)* | ❌ no | ❌ no |
| 4 | `descripcion` | `text` | *(vacío)* | ✅ sí | ❌ no |
| 5 | `activo` | `bool` | `true` | ❌ no | ❌ no |
| 6 | `orden` | `int4` | `0` | ✅ sí | ❌ no |
| 7 | `metadata` | `jsonb` | `'{}'::jsonb` | ❌ no | ❌ no |
| 8 | `created_at` | `timestamptz` | `now()` | ❌ no | ❌ no |
| 9 | `updated_at` | `timestamptz` | `now()` | ❌ no | ❌ no |

> En el panel el tipo `bool` aparece como **bool**; `int4` como **int4** o **integer**; `timestamptz`
> como **timestamptz**. Son los mismos tipos.

6. **Save.**

### Por qué cada columna

| Columna | Motivo |
|---|---|
| `id uuid` | Identidad técnica. Nunca se reutiliza ni se muestra al usuario. |
| `codigo` | El valor que otras tablas guardarán (`en_curso`). Es el identificador de negocio. |
| `nombre` | Lo que ve el usuario ("En curso"). Puede cambiar sin romper nada. |
| `descripcion` | Texto de ayuda opcional. |
| `activo` | Retirar un estado sin borrarlo: los proyectos históricos siguen siendo válidos. |
| `orden` | Orden de aparición en el desplegable, decidido por negocio y no por alfabeto. |
| `metadata` | Crecimiento sin migrar (por ejemplo un `color` o un `icono`). |
| `created_at` / `updated_at` | Auditoría mínima. |

## Paso 2 · Restricción de unicidad sobre `codigo`

Debe existir **una sola** fila "en_curso". En el panel: menú de la tabla → **Edit table** →
**Add constraint** → tipo `UNIQUE`, columna `codigo`, nombre `uq_gp_estados_proyecto_c_codigo`.

Si tu versión del panel no tiene ese diálogo, ejecuta esta línea en **SQL Editor** (es la misma que
genera el panel, por eso no cuenta como "hacerlo por SQL"):

```sql
alter table public.gp_estados_proyecto_c
  add constraint uq_gp_estados_proyecto_c_codigo unique (codigo);
```

**No** se agrega ningún `CHECK` sobre el formato de `codigo` en este paso: el archivo `0001` no lo
tiene y la paridad manda.

### Índices resultantes (los crea el motor, no se escriben)

| Índice | Origen | Para qué |
|---|---|---|
| `gp_estados_proyecto_c_pkey` | Primary key | Buscar por `id`. |
| `uq_gp_estados_proyecto_c_codigo` | UNIQUE | Garantizar unicidad y acelerar el `join` por `codigo`. |

No hace falta más: son 5 filas.

## Paso 4 · Activar RLS y crear las 4 políticas

**Table Editor → `gp_estados_proyecto_c` → RLS** (o *Authentication → Policies → New policy*).
Comprueba que **RLS está habilitado** y crea una política por operación, desde cero
(*Create policy from scratch*), sin usar las plantillas genéricas.

### 4.1 SELECT — leer la lista

- **Policy name:** `gp_estados_proyecto_c_select`
- **Allowed operation:** `SELECT`
- **Target roles:** `authenticated`
- **USING expression:**

```sql
public.is_tenant_member() or public.is_platform_admin()
```

### 4.2 INSERT — solo plataforma

- **Policy name:** `gp_estados_proyecto_c_insert`
- **Allowed operation:** `INSERT`
- **Target roles:** `authenticated`
- **WITH CHECK expression:**

```sql
public.is_platform_admin()
```

### 4.3 UPDATE — solo plataforma

- **Policy name:** `gp_estados_proyecto_c_update`
- **Allowed operation:** `UPDATE`
- **Target roles:** `authenticated`
- **USING:** `public.is_platform_admin()`
- **WITH CHECK:** `public.is_platform_admin()`

### 4.4 DELETE — solo plataforma

- **Policy name:** `gp_estados_proyecto_c_delete`
- **Allowed operation:** `DELETE`
- **Target roles:** `authenticated`
- **USING:** `public.is_platform_admin()`

### Por qué el SELECT es más amplio

Un catálogo **no contiene información privada**: no hay nombre de cliente, ni montos, ni personas.
El Hub ya hace esto mismo con `app_catalog` (`for select using (true)`). Aquí se es un paso más
estricto: se exige ser miembro de una empresa del Hub (`is_tenant_member()`), no basta con estar
autenticado. **Esta excepción no se repite** en `gp_proyectos`, `gp_personas` ni en ninguna tabla con
datos de negocio: ahí manda `empresa_id = get_auth_tenant_id()`.

La escritura queda en manos de plataforma porque el catálogo define el comportamiento de la app: si
cualquier empresa pudiera añadir estados, cada una tendría un modelo distinto y los reportes dejarían
de ser comparables.

### Permisos (grants)

RLS filtra filas; los *grants* deciden si el rol puede intentar la operación. En **SQL Editor**:

```sql
revoke all on public.gp_estados_proyecto_c from anon;
grant select, insert, update, delete on public.gp_estados_proyecto_c to authenticated;
```

- `anon` (visitante sin sesión) no toca la tabla.
- `authenticated` puede *intentar* las cuatro operaciones; la RLS decide cuáles prosperan.
- `service_role` (backend, tareas administrativas) queda fuera de RLS por diseño de Supabase.

## Paso 5 · Verificar que funciona

### 5.1 · Que exista lo que creemos

```sql
-- 9 columnas, tipos y nulabilidad
select column_name, data_type, is_nullable, column_default
from information_schema.columns
where table_schema = 'public' and table_name = 'gp_estados_proyecto_c'
order by ordinal_position;

-- constraints e índices
select conname, pg_get_constraintdef(oid) as definicion
from pg_constraint
where conrelid = 'public.gp_estados_proyecto_c'::regclass;

select indexname, indexdef from pg_indexes
where schemaname = 'public' and tablename = 'gp_estados_proyecto_c';

-- RLS activo
select relname, relrowsecurity as rls_activo, relforcerowsecurity as rls_forzado
from pg_class where oid = 'public.gp_estados_proyecto_c'::regclass;
```

Esperado: 9 columnas · 2 constraints (`..._pkey`, `uq_..._codigo`) · 2 índices · `rls_activo = true`.

### 5.2 · Que las políticas sean las 4 correctas

```sql
select policyname, cmd, roles, qual, with_check
from pg_policies
where schemaname = 'public' and tablename = 'gp_estados_proyecto_c'
order by cmd;
```

Esperado: `SELECT, INSERT, UPDATE, DELETE` y **ninguna** con `qual = 'true'`.

### 5.3 · Prueba real como usuario (positiva y negativa)

Sustituye `<UUID_DEL_USUARIO>` por el `id` de un usuario real de `public.users` (Table Editor →
`users` → copiar `id`). Todo ocurre dentro de una transacción que se revierte: **no modifica nada**.

```sql
begin;
set local role authenticated;
set local request.jwt.claims = '{"sub":"<UUID_DEL_USUARIO>","role":"authenticated"}';

-- 1) ¿ve el catálogo?  -> debe devolver 5
select count(*) as filas_visibles from public.gp_estados_proyecto_c;

-- 2) ¿puede escribir?   -> debe fallar o afectar 0 filas
update public.gp_estados_proyecto_c set nombre = 'hackeado' where codigo = 'en_curso';

rollback;
```

**Negativa (aislamiento):** repite la prueba 1 con un `sub` inventado (un UUID aleatorio que no
existe en `public.users`) → debe devolver **0**. Eso demuestra que un desconocido no lee nada.

> Si además quieres ver el aislamiento por empresa de verdad, esa prueba llega en la TABLA 02
> (`gp_personas`), que sí tiene `empresa_id`.
