## 1 · Verificación de plataforma y legacy

Pegar en **SQL Editor → Run**:

```sql
select
  t.nombre                                   as objeto_requerido,
  (c.oid is not null)                        as existe,
  coalesce(c.reltuples::bigint, 0)           as filas_aprox
from (values
  ('public.tenants'),
  ('public.users'),
  ('public.gestor_unidades'),
  ('public.user_app_roles'),
  ('public.gestor_proyectos'),
  ('public.gestor_cronograma_items'),
  ('public.app_catalog'),
  ('public.tenant_app_subscriptions')
) as t(nombre)
left join pg_class c on c.oid = to_regclass(t.nombre);
```

### Resultado esperado y para qué se usa cada uno

| Objeto | Debe ser | Uso en el modelo |
|---|---|---|
| `public.tenants` | `true` | `empresa_id` de TODAS las tablas de negocio (0002/0003) |
| `public.users` | `true` | `gp_personas.user_id` (0002) |
| `public.gestor_unidades` | `true` | `gp_nodos_edt.sede_unidad_id` y `gp_proyecto_unidades_r.unidad_id` (M-7). Debe tener ≈ 251 filas |
| `public.user_app_roles` | `true` | Helpers RLS del 0004 (`gp_is_empresa_member`, `gp_auth_empresa_id`) — **verificar que tenga columnas `user_id` y `empresa_id`** |
| `public.gestor_proyectos` | `true` | Legacy: origen del backfill 0100 (solo lectura) |
| `public.gestor_cronograma_items` | `true` | Legacy: origen del backfill. Columnas esperadas: base de `01` + `baseline_start/baseline_end/actual_start/actual_end` (migración `02`). **NO asumir** `task_type`, `icon`, `fase_id`, `metadata`, `edt_type`, `empresa_id` — NO existen en la BD viva (`04` sin evidencia de aplicación; el backfill v3.1 los deja NULL y el merge P-1 los completa) |
| `public.app_catalog` / `tenant_app_subscriptions` | `true` (opcional en este paso) | Solo relevantes para la RLS por app; conviene saberlo desde ahora |

**Si `tenants`, `users` o `gestor_unidades` salen `false`: detenerse.** Falta una migración de
plataforma/legacy; no es un error del diseño y no se crea nada hasta resolverlo.

## 5 · Columnas reales de la legacy y prevalidación de duplicados (A-6)

**Evidencia viva reportada (13-nov):** `gestor_cronograma_items` ≈ **6.699 filas**, **1 solo
proyecto**, `kind` solo `hito`/`subproceso`. NO existen en vivo: `task_type`, `icon`,
`fase_id`, `metadata`, `edt_type`, `empresa_id` (la migración `04` no tiene evidencia de
aplicación). SÍ existen: columnas base de `01` y `baseline_start/end`, `actual_start/end`
(`02`).

```sql
-- a) Columnas REALES de gestor_cronograma_items (contrastar con lo que asume el backfill)
select column_name, data_type
from information_schema.columns
where table_schema = 'public' and table_name = 'gestor_cronograma_items'
order by ordinal_position;

-- b) Duplicados que abortarían el backfill [prevalidación A-6 §0]: deben salir 0 filas
select project_id, coalesce(code, id) as codigo, count(*)
from public.gestor_cronograma_items
group by project_id, coalesce(code, id)
having count(*) > 1;

select coalesce(code, id) as codigo, count(*)
from public.gestor_proyectos
group by coalesce(code, id)
having count(*) > 1;
```

- Si (a) muestra `task_type`/`icon`: anótalo; el backfill v3.1 igualmente escribe NULL
  (opción (b) del punto 2) y el merge P-1 trae los valores desde localStorage.
- Si (b) devuelve filas: el Paso 5 abortará en la PREVALIDACION [A-6] sin insertar nada;
  corregir los códigos en origen antes de ejecutarlo.
